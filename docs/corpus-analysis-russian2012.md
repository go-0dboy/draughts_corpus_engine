# Анализ реального корпуса `russian2012.pdn`

Этот документ фиксирует требования, полученные не из предположений, а из полного scan предоставленного корпуса. Корпус используется как эталонная выборка для проектирования importer-а и corpus builder-а.

## Масштаб

- размер исходного файла: ~64 MB;
- партий: **109 616**;
- строк: ~1,8 млн;
- распознано алгебраических записей ходов: ~**5,2 млн**;
- стартовых позиций через `FEN`: **6 496**;
- у каждой найденной партии присутствуют `White`, `Black`, `Event`, `Round`, `Site`, `Date`, `Result`, `GameType`;
- `GameType`: во всех партиях **25** (русские шашки).

Распределение результатов:

| Результат | Партий |
|---|---:|
| `1-1` | 69 026 |
| `2-0` | 20 441 |
| `0-2` | 19 238 |
| `*` | 911 |

Следствие: статистическое ядро обязано понимать default draughts result (`2-0`, `1-1`, `0-2`), а не только шахматные `1-0`, `1/2-1/2`, `0-1`.

## Реальный порядок заголовков

Типичный блок корпуса:

```pdn
[White "..."]
[Black "..."]
[Event "..."]
[Round "..."]
[Site "..."]
[Date "..."]
[Result "2-0"]
[GameType "25"]
```

В 6 496 партиях после `GameType` добавляется `FEN`.

**Вывод:** нельзя определять начало партии по `[Event ...]`. Порядок тегов не является частью доменной модели. Reader должен читать последовательность header tags как единый header block и определять границу игры синтаксически.

## Нотация ходов

Корпус использует буквенные поля `a1-h8`, что соответствует нашему требованию к пользовательской нотации.

Тихие ходы:

```text
c3-b4
f6-e5
```

Взятия в историческом корпусе почти всегда записаны через `x`:

```text
g5xe3
d2xf4
```

Статистика найденных разделителей:

- `-`: ~3 742 189 записей;
- `x`: ~1 464 094 записей;
- `:`: 47 записей.

PDN 3.0 задаёт для `GameType 25` предпочтительный capture separator `:`, но liberal reading grammar допускает `[x:]`. Поэтому:

- reader принимает `x` и `:`;
- исходная запись сохраняется;
- внутренняя модель хода не зависит от текстового separator;
- writer нового PDN может сериализовать канонический `:`.

## Сокращённые взятия — критическое требование

В корпусе встречаются записи вроде:

```text
a3xe3
c5xc1
c7xa1
```

То есть начальная и конечная клетки могут не лежать на одной диагонали. Это сокращённая запись многошагового взятия, а не один геометрический прыжок.

Полных записей с несколькими явными `x`/`:` очень мало по сравнению со всем корпусом. Следовательно, простой алгоритм `from -> to` **не способен восстановить позицию**.

Правильный алгоритм:

1. построить все легальные ходы текущей позиции;
2. для записи тихого хода найти ход по `from/to`;
3. для взятия построить все легальные capture sequences;
4. отфильтровать по `from`, `to` и, если в PDN указан полный путь, по пути;
5. если кандидат один — применить его;
6. если кандидатов несколько — диагностировать неоднозначность, а не угадывать;
7. если кандидатов нет — сохранить партию и диагностировать несовместимую запись.

Именно поэтому полный Rules Engine должен находиться **в ядре библиотеки** и использоваться importer-ом.

## Комментарии, варианты и аннотации

В корпусе обнаружены:

- более 11 тыс. блоков комментариев `{ ... }`;
- десятки тысяч RAV/вариантов `( ... )`;
- более 3 тыс. NAG `$n`;
- отдельные старые/неформальные конструкции внутри комментариев;
- 6 496 FEN с цифровой адресацией полей — их надо читать как legacy input, но не показывать как пользовательскую нотацию.

Reader не должен терять эти данные. Для Position Index на первом проходе используется main line, но AST/исходный текст сохраняются для последующего просмотра и lossless export.

## Почему текущий браузерный импорт не масштабируется

Текущая схема `File -> file.text() -> огромный JS string -> массив всех Game/Move/Position` неприемлема для корпуса такого размера:

- блокирует UI thread;
- создаёт множество JS-объектов для миллионов ходов;
- удваивает/утраивает память из-за исходного текста, токенов и позиций;
- заставляет повторять дорогой импорт после перезапуска.

### Решение

Разделяем два сценария.

### 1. Published Corpus

Большой исторический корпус обрабатывается **офлайн Node.js corpus builder-ом** и превращается в готовую индексированную БД/набор бинарных блоков. Мобильное приложение не парсит 64 MB PDN при каждом запуске.

```text
PDN source
   -> tolerant reader
   -> rules/replay
   -> normalize/deduplicate
   -> build positions/transitions/indexes
   -> published corpus database
```

### 2. User Library

Новые пользовательские PDN импортируются инкрементально локально:

```text
File picker
   -> Worker/streaming reader
   -> rules/replay
   -> local repository adapter
   -> indexes
```

Официальный корпус и пользовательская библиотека физически/логически разделены, но запросы Corpus API объединяют их результаты.

## Требования к импорт-отчёту

Importer возвращает структурированный отчёт, а не только `throw Error`:

```ts
interface ImportReport {
  discoveredGames: number;
  parsedGames: number;
  replayedGames: number;
  indexedGames: number;
  warnings: Diagnostic[];
  errors: Diagnostic[];
}
```

Диагностика должна содержать:

- номер/идентификатор партии;
- фазу (`header`, `pdn`, `notation`, `rules`, `storage`);
- номер хода при наличии;
- исходный фрагмент;
- тип проблемы;
- severity.

Одна проблемная партия не должна останавливать импорт остальных 100 тысяч.

## Архитектурное следствие

Корпус подтвердил необходимость архитектуры **library first**:

```text
@draughts/core
  board / position / rules / move generation / notation

@draughts/pdn
  tolerant reader / AST / writer / diagnostics

@draughts/corpus
  games / position dictionary / transitions / queries

@draughts/storage
  repository interfaces + adapters

@draughts/tools
  plugin contracts / registry

mobile app
  только UI + orchestration через публичный API библиотек
```

UI не должен знать, как устроены bitboard, PDN parser или конкретная БД.

## Критерий совместимости с `russian2012.pdn`

Корпус считается поддержанным, когда автоматический integration test/build pipeline:

1. обнаруживает все 109 616 партий;
2. не теряет headers/source;
3. корректно классифицирует четыре типа результата;
4. читает `x` и `:`;
5. читает legacy numeric FEN;
6. сохраняет comments/RAV/NAG в AST/source;
7. воспроизводит main line через Rules Engine;
8. выдаёт исчерпывающий отчёт по партиям, которые невозможно однозначно воспроизвести;
9. строит позиционный индекс без блокирования мобильного UI.
