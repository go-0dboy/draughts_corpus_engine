# Review предыдущего прототипа и решения по переносу

Этот документ фиксирует решения после разбора присланных модулей предыдущей разработки. Цель — не переносить код механически, а сохранить удачные границы модулей и проверенные UX/PDN решения в новой library-first архитектуре.

## engine.js

### Переносим как поведение

- rules engine не зависит от DOM;
- отдельные функции `getLegalMoves` и `getMovesForPiece`;
- обязательность взятия;
- простая бьёт назад;
- летающая дамка;
- превращение во время серии действует сразу;
- снятые фигуры блокируют путь до завершения серии;
- алгебраическое имя клетки отделено от внутреннего индекса.

### Не переносим как внутреннее представление

Старый движок использует массив 64 клеток. Новый corpus engine сохраняет bitboard-модель как каноническое представление позиции. При необходимости для отдельных алгоритмов допускается временное преобразование, но публичная domain model не должна зависеть от массива 64.

### Не переносим

Эвристику «две дамки на доске = ничья» нельзя использовать как общее правило окончания партии. Результат исторической партии берётся из источника; полноценные правила ничьей должны быть реализованы отдельно и подтверждены правилами вида игры.

## pdn.js

### Переносим

Ключевой принцип: **читать либерально, писать строго**.

Reader должен понимать:

- `x`, `:` и `×` как исторические/допустимые входные разделители взятия;
- лидирующие нули и старые формы записи;
- комментарии;
- NAG/аннотации;
- вложенные варианты;
- setup/FEN;
- повреждённые/OCR-фрагменты без потери всей партии.

Writer должен генерировать канонический PDN выбранного GameType.

### Меняем архитектуру

Старый parser непосредственно вызывает rules engine во время разбора. В новом проекте pipeline разделяется:

```text
text
 -> lexer
 -> syntax/AST
 -> rules resolver
 -> domain Game/GameTree
 -> corpus builder/storage
```

Благодаря этому синтаксически прочитанная партия не исчезает из-за одного неразрешимого хода.

### Batch import

Старый `parsePDNBatch` намеренно отвергает партии с комментариями/вариантами для некоторых сценариев. Для исторического корпуса это ограничение неприемлемо: новый builder должен сохранять исходную структуру, а для позиционного индекса отдельно выбирать main line.

## history.js

### Переносим

- `children[0]` = main line;
- `children[1..]` = variations;
- комментарии разделяются на `commentsBefore` и `commentsAfter`;
- annotation принадлежит конкретному ходу;
- переход по дереву отделён от правил.

### Меняем

Старый `GameHistory` содержит DOM container и parent links. Новая domain-модель `GameTree` сериализуема:

- без DOM;
- без циклических parent references;
- пригодна для IndexedDB/SQLite serialization;
- пригодна для передачи Web Worker.

UI navigation строит собственный view state поверх domain tree.

## board.js

### Переносим

Самый удачный принцип модуля: **доска ничего не знает о правилах**.

Она только:

- отображает состояние;
- показывает selected/last move/hints/movable;
- обрабатывает click/drag;
- сообщает user intent наружу;
- умеет flip;
- отдельно рендерит координаты вокруг игрового поля.

Новая React `Board` должна сохранять ту же границу ответственности.

### Геометрия

Координаты находятся в frame rails вокруг чистой сетки 8×8. Они не должны занимать место внутри клеток.

Игровая поверхность всегда:

```css
grid-template-columns: repeat(8, 1fr);
grid-template-rows: repeat(8, 1fr);
aspect-ratio: 1;
```

## themes.js

### Переносим

Тема приложения и скин доски — независимые настройки.

```text
App theme  -> surfaces / typography / navigation
Board skin -> frame / squares / pieces
```

Board skin не должен перекрашивать всё приложение.

Новая реализация использует typed preferences + CSS variables вместо прямой DOM-логики.

## settings.js

### Переносим

- сохранение пользовательских preferences;
- выбор темы;
- выбор board skin;
- future engine/resource settings должны жить отдельно от rules engine.

### Не переносим в мобильный UI

Desktop-концепцию произвольного расположения панелей слева/справа и ручного порядка колонок. Mobile-first приложение использует routes, bottom sheets и contextual actions. Tablet layout адаптируется автоматически, а не превращается в конструктор desktop-панелей в MVP.

## storage.js

### Переносим

Чёткое разделение storage/I-O и игровой логики:

- file read;
- file save;
- clipboard;
- preferences.

Fallback важен: API, доступное desktop browser, может отсутствовать в Android WebView/mobile browser.

В новом приложении этот контракт позже будет иметь adapters:

```text
Web adapter
Capacitor Android adapter
Corpus DB adapter
```

## export.js

### Переносим позже как tool

Хорошая идея — экспорт позиции не обязан зависеть от текущей UI-темы. Для share/export используется стабильная читаемая палитра.

Это должен быть подключаемый инструмент `position.export`, а не ответственность компонента Board.

## toast.js

### Переносим как UX-паттерн, не как DOM-код

Короткие success/error сообщения полезны для:

- импорт завершён;
- файл сохранён;
- FEN скопирован;
- ошибка действия.

В React/Android-shell это будет snackbar/toast service с очередью сообщений и accessibility live region.

## Итоговая граница модулей

```text
UI / Android shell
       |
Application services + preferences
       |
Domain: Game / GameTree / Position
       |
+-------------+--------------+----------------+
| Rules Core  | PDN pipeline | Corpus API     |
+-------------+--------------+----------------+
                              |
                        Storage adapters

Tools Registry -> работает только через публичные Domain/Corpus API
```

Главный принцип миграции: переносим знания и границы ответственности, а не старую desktop-структуру приложения.
